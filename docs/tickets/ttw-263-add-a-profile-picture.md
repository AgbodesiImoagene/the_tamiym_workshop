## Background

The approved Figma shows a round profile photo on the Profile and Settings pages (with an "Upload Profile Picture" / "Update Profile Picture" button) and in the sidebar next to the name. `apps/app` shows initials in a grey circle and no upload (TTW-253, rows 1, 4 and 5).

History: TTW-091 removed the fake demo photo and its inactive button because the client answered "up to you, happy to remove for simplicity" (Q10). The product owner now wants the real feature, as in Figma. This is not a client-blocking decision (Q10 left it open), but the ticket is recorded so the reversal is visible.

`User` has no image field (`apps/api/prisma/schema.prisma`, model `User`). The API already has what an upload needs: `sharp`, a private bucket (`S3Service.uploadPrivateObject`, TTW-099), byte-level image identification (`identifyImageBuffer`) and a virus scanner (`VirusScanService`).

## Proposal

- **Storage:** private bucket only, key `avatars/<userId>/<random id>.webp`. No public URL, no ACL. The bytes are read through an authenticated API route, like design assets (`GET /design-assets/:id/file`).
- **Compression, server side (always):** scan the raw bytes first, identify the format from the decoder (JPEG, PNG, WebP; never from the client's MIME or file name), then square-crop and resize to at most 256 px and re-encode as WebP quality 80. EXIF and other metadata are dropped. The original is never stored.
- **Compression, browser side (bandwidth):** the app downsizes to at most 1024 px with a canvas before sending. The server does not rely on it.
- **API:**
  - `User.avatarKey String?` (Prisma migration generated by the CLI).
  - `POST /v1/users/profile/avatar` (multipart `file`, 5 MB max), `DELETE` and `GET` on the same path. Rate limited to 10 uploads a minute per caller (`ThrottlerGuard`, as the privacy routes do: the throttler is not global). Fails closed when the scanner or the private bucket is unavailable.
  - `GET /auth/me` returns `avatarVersion` (the random id of the current object, or `null`), never the key. The app builds `…/users/profile/avatar?v=<avatarVersion>` and caches on that version.
- **App:** a shared `Avatar` (photo or initials) in the sidebar, Profile and Settings; an upload button wired to the API with loading, error and remove states. All text in English.
- A new upload writes the new object, updates the row, then deletes the old object (a failed delete is logged and never blocks the user; a leftover object is private, unreferenced and unreadable, so no sweep is built for it).

Rejected: public bucket (the product owner chose private); processing in the BullMQ media queue (the user waits for the result and the image is tiny, so it is done in the request); storing the original (no use for it, more to protect).

## Invariants

- A user can only read, replace or delete their own picture. No route takes a user id.
- The stored object is always a WebP of at most 256 × 256 produced by the server, whatever the client sent.
- Nothing in the database, logs or API responses contains the storage key or a signed link.
- A scanner or bucket outage never lets an unscanned file through.
- Behaviour outside this ticket (settings form, password, shipping) is unchanged.

## Test and observability plan

- Unit/component (API): a 4 000 × 3 000 JPEG comes out as WebP ≤ 256 px and far smaller; a PNG with an alpha channel works; a text file renamed `.jpg` is refused (400); a file over 5 MB is refused; an infected or scanner-failed file is refused and nothing is stored; replacing deletes the previous object; delete clears the row and the object; reading another user's picture is impossible (no id in the route); `/auth/me` returns `avatarVersion` and never `avatarKey`.
- Unit/component (app): `Avatar` shows the photo, falls back to initials on error and when there is none; the upload control shows loading and error, refuses a non-image before sending, and downsizes a large image.
- Integration/e2e: Playwright uploads a picture on Profile and sees it in the sidebar, then removes it. Needs MinIO.
- Failure, retry, and concurrency: two uploads at once leave exactly one object referenced (the loser's object is deleted); storage down returns 5xx without changing the row.
- Logs, metrics, traces, and alerts: a counter and a log line for upload outcome (accepted, rejected, scan failed), with no file name, key or user email.

## Implementation reviews

Independent security review (separate subagent, read-only, 2026-11-25): **PASS, no blocker**. Four should-fix points, all fixed:

1. Account erasure kept the picture. Fixed: `privacy.service.ts` clears `avatarKey` in the erasure transaction and deletes the object after commit (`UserAvatarService.purgeObject`). Test: `privacy.service.spec.ts` "erases the profile picture with the account (TTW-263)".
2. No rate limit although the ticket promised one. Fixed: `@Throttle` 10/min per signed-in user (`UserThrottlerGuard`, keyed by user id, not IP). Tests: `user-throttler.guard.spec.ts`, e2e "refuses an eleventh upload".
3. Error answers cacheable for 24 h. Fixed: `Cache-Control` is set in the handler, only on a 200. Tests: controller spec and e2e "lets only a successful read be cached, never an error".
4. Orphaned objects not swept. Decision: no sweep (a leftover is private, unreferenced and unreadable); the ticket text was corrected.

Also done from the review: cookie/CSRF e2e (403 without the token on POST and DELETE), decompression-bomb test (52 MP PNG refused), `naturalWidth` check in Playwright, multer `files: 1, fields: 0, parts: 1`. Not done, on purpose: magic-byte pre-check before sharp (sharp already restricts formats), per-avatar pixel cap below the shared 50 MP, theme token for `#004385` (same colour as the existing Save buttons).
