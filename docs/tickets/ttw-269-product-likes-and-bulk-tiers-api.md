# TTW-269 — Add product likes and bulk pricing tiers to the product API

**Blocks:** The likes counter and the bulk price table of the customer product page

## Background

The product owner wants the customer product page to show a likes counter, reviews and all product data. This ticket covers the API for likes and bulk tiers. Decisions given by the product owner: a like is on the **product**, one per customer, and can be removed. Reviews are for buyers only and belong to TTW-270.

Today:

- No model, endpoint or field records a like (`apps/api/prisma/schema.prisma:988`, model `Product`).
- `GET /v1/products/:id` does not return bulk pricing tiers (`apps/api/src/products/products.service.ts:309`, `findOne`), although the list returns one summary tier (`products.service.ts:286`).
- `GET /v1/products/:id` is public and answers the same body to everybody (`apps/api/src/products/products.controller.ts:109`).

## Proposal

### Data

A `ProductLike` model (`product_likes`): `id`, `userId`, `productId`, `createdAt`; `@@unique([userId, productId])`, `@@index([productId])`; both relations `onDelete: Cascade`. The count is computed with `COUNT`.

### Contract

| Call                           | Access    | Answer                                   |
| ------------------------------ | --------- | ---------------------------------------- |
| `GET /v1/products/:id`         | Public    | Existing body plus `likeCount` and tiers |
| `GET /v1/products/:id/like`    | Signed in | `{ productId, likedByMe, likeCount }`    |
| `PUT /v1/products/:id/like`    | Signed in | Same; the product is now liked           |
| `DELETE /v1/products/:id/like` | Signed in | Same; the product is now not liked       |

- All three like calls answer 200, are idempotent, take no body and act only on the user of the session. 401 without a valid session, 404 for an unknown or non-`ACTIVE` product, 403 for a cookie request without the CSRF token (`PUT`, `DELETE`).
- Detail tiers: `bulkPricingTiers` on the product holds the product-level tiers (`variantId` null); each `variants[].bulkPricingTiers` holds that variant's own tiers (usually empty). Both: NGN only, ordered by `minQuantity`, items `{ minQuantity, maxQuantity, pricePerUnit, currency }` with `pricePerUnit` a number, as in the list `bulkTier`. A variant with its own tiers replaces the product tiers. Display only: the server quote stays the price authority.

### Deliberate decisions

- **`likedByMe` is not in the public detail.** With an optional session (`OptionalJwtAuthGuard`) an expired access token would answer `likedByMe: false` with 200, so the app would not renew the session and would show a wrong heart; the public body would also depend on the reader. The separate authenticated `GET …/like` avoids both, at the cost of one more request on the product page.
- `PUT`/`DELETE` rather than a toggle: a repeated or replayed call cannot invert the state.
- Insert with `createMany({ skipDuplicates: true })` (`ON CONFLICT DO NOTHING`) and remove with `deleteMany`, so concurrent duplicates never raise. The database constraint is the guarantee.
- No denormalised counter on `Product`: nothing to drift.
- Any signed-in account may like, as for the other customer routes (no role check).
- A like is written in a transaction that first takes a shared lock on the **active** user row (`SELECT … FOR SHARE`), so it cannot slip past an erasure in progress; it then answers 401.
- `likedByMe` and `likeCount` are read in one `RepeatableRead` snapshot.
- Account erasure deletes the user's likes (the count goes down), and the data export lists them. Erasure keeps the user row, so the cascade alone would not remove them.
- No rate limit of its own: rows are bounded by one per user and product.

## Invariants

- At most one like exists per (user, product), enforced by the database.
- A user can only create, read or remove their own like; no request field names a user.
- `likeCount` equals the number of `product_likes` rows of the product.
- The public detail never says who liked a product.
- An erased account keeps no like.
- Quotes and order prices are unchanged.

## Design review

Reviewer: implementing session (Claude), 2026-11-25.

- Blast radius: one new table, three new routes, additive fields on the public detail, erasure and export. No existing field changes type or disappears.
- Duplication: no like or favourite exists; tier shape follows the list `bulkTier`.
- Interfaces: see the contract table.
- Edge cases: unknown, draft and archived product (a like on a product that is later archived stays and cannot be removed until it is active again); product hard-deleted during a like (404); repeated and concurrent calls; expired session (401, so the client renews it); admin-surface session accepted.
- Security: session user only, global JWT and CSRF guards, no body, no list of likers. The race with account erasure first noted here is closed (see Implementation reviews).
- Risks: merge conflicts with TTW-266 and TTW-267; `COUNT` per detail request (indexed).
- Verdict: ready to implement once the user approves the plan.
