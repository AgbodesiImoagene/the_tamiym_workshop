# Playwright regression strategy

## Decision

Playwright becomes the browser-level acceptance layer for `web`, `app`, and `admin`. Every UI-affecting ticket must add or update the tests for the behaviour it changes. The suite is built incrementally with product work; it is not a final release-phase exercise.

The current baseline has no Playwright dependency, configuration, fixtures, or CI job. Browser coverage consists of three Jest workshop component suites in `apps/app`, one of which currently fails. The repository therefore has no automated proof that its multi-application business journeys work end to end.

## What this layer proves

Playwright must prove observable user outcomes and the important API/data side effects behind them:

- anonymous, customer, organiser, and admin access boundaries;
- navigation, forms, validation, loading, empty, error, success, refresh, and retry states;
- responsive and keyboard behaviour on critical paths;
- cross-surface journeys spanning public site, customer app, admin, API, and signed provider webhooks;
- pricing, inventory, order, campaign, refund, and payout state shown consistently after mutation;
- regressions in stable high-value visual regions and automatically detectable accessibility defects.

Unit tests remain the fastest check for calculations and state machines. API integration tests prove database and concurrency invariants. Playwright proves that deployable applications connect those layers into a usable business journey.

## Test architecture

Create a root `playwright.config.ts` and `tests/e2e/` with:

```text
tests/e2e/
  setup/              environment, seed and role authentication projects
  fixtures/           per-worker identities, API clients and provider simulator
  pages/              small page objects for repeated interaction only
  web/                anonymous marketing and fundraiser commerce
  app/                customer and organiser workflows
  admin/              operations and administration
  journeys/           multi-role, cross-application business lifecycles
  accessibility/      axe scans and keyboard checks
  visual/             intentionally small stable snapshot set
```

Use a dedicated E2E environment with disposable PostgreSQL, Redis and object storage. Use a deterministic mail sink, moderation stub and local Paystack simulator capable of returning initialization responses and emitting correctly signed, duplicated, delayed, failed and out-of-order webhooks. Never call live Paystack from ordinary CI.

Seed immutable reference data once per run. Create mutable users, campaigns and orders per worker or per test with unique namespaces. Database reset/seed and authentication are Playwright setup-project dependencies so setup has normal reporting and traces. Authentication state is generated by API-assisted login for customer, organiser and admin roles, stored under an ignored output directory, and never committed. Tests that mutate shared server state must not share accounts.

Configure separate projects and base URLs for the three applications. Use Chromium desktop as the pull-request baseline; add mobile Chromium for responsive critical paths, and run Firefox, WebKit and mobile Safari in the scheduled full matrix. Keep admin and customer storage states strictly separate and include explicit negative tests for cross-surface cookie use.

## Canonical cross-surface journeys

1. Admin publishes a stocked product and workshop configuration; customer designs it, saves, shares, carts, checks out, receives payment confirmation, and sees the order.
2. Admin promotes an eligible customer to organiser; organiser creates a campaign, attaches an approved design and valid price, submits it, admin reviews it, and the public page becomes purchasable.
3. Supporter enters from a shared fundraiser link, authenticates without losing selections, purchases, and the organiser/admin totals update exactly once after duplicate `charge.success` delivery.
4. Admin progresses a paid order through processing, fulfilment and delivery; inventory and customer-visible status remain consistent and notifications are emitted once.
5. Admin requests a partial/full refund; delayed and duplicate provider events settle it once, campaign totals/ledger reconcile, and the customer sees the correct result.
6. Eligible campaign funds enter a payout run, receive separate approval, execute through the provider simulator, and remain correct under duplicate/failure/reversal events.

## Assertion and locator rules

- Prefer role, label, placeholder and visible text locators. Add `data-testid` only when a stable user-facing locator is impossible.
- Assert the business outcome, not implementation trivia: visible status plus an API or database invariant for money and inventory mutations.
- Synchronize on URL, response, state or element expectations. Never add arbitrary sleeps.
- Treat unexpected console errors, unhandled page errors and failed non-allowlisted requests as test failures.
- Do not intercept the API for core acceptance flows. Network stubs are reserved for external providers and deliberate frontend error-state tests.
- Retries expose flakes; they do not make a red test green. A test that passes only on retry is quarantined with an owner and ticket, then fixed promptly.

## Accessibility and visual regression

Run `@axe-core/playwright` on one representative page per major template and after opening important dialogs. Include keyboard-only checks for navigation, workshop controls, checkout, moderation and destructive confirmations. Automated scans supplement, but do not replace, manual screen-reader and keyboard UAT.

Keep visual baselines limited to stable, high-value layouts: public fundraiser desktop/mobile, customer dashboard, workshop shell with deterministic canvas content, checkout review, admin dashboard and one dense admin detail page. Mask dates, IDs, animated/loading regions and user-generated images. Snapshot changes require an intentional design review; never bulk-update them merely to pass CI.

## Execution tiers

| Gate              | When             | Scope                                                                                 | Target                  |
| ----------------- | ---------------- | ------------------------------------------------------------------------------------- | ----------------------- |
| Smoke             | every PR         | Chromium, all three apps, health/auth/navigation plus one read-only critical page     | under 10 minutes        |
| Ticket acceptance | every UI PR      | tagged feature specs and relevant cross-surface journey                               | required, no failures   |
| Main regression   | merge to `main`  | full Chromium plus critical mobile Chromium                                           | required, shardable     |
| Browser matrix    | nightly          | Firefox, WebKit, mobile Chromium/Safari, accessibility and stable visuals             | required before release |
| Staging release   | candidate/deploy | production builds and infrastructure; read-only plus controlled transaction lifecycle | release blocking        |

CI uploads the HTML report and traces on first retry; retain screenshots/video only on failure. Shard the full suite by historical duration once runtime warrants it. Tests are tagged `@smoke`, `@critical`, `@web`, `@app`, `@admin`, `@journey`, `@a11y`, and `@visual` so ticket and release gates select scope explicitly.

## Definition of comprehensive

Comprehensive does not mean maximizing test count. Release coverage is complete when:

- every route and interactive control is present in the feature inventory;
- every PRD journey has at least one end-to-end happy path;
- every critical money, authorization and inventory journey has failure, retry, duplicate and concurrency coverage split appropriately between integration and Playwright;
- desktop and supported mobile layouts, Chromium/Firefox/WebKit, accessibility, and intentional visual checks are represented;
- every production incident or escaped regression adds a reproducing test;
- the full required suite is green with no unowned quarantine.

## Adoption sequence

1. Repair the Node/CI and integration-test baseline.
2. Add Playwright, service orchestration, deterministic seeds, provider simulator, auth fixtures, reports and the three-app smoke suite.
3. Cover the critical financial and session-isolation corrections as they are implemented.
4. Add one feature group per business ticket, prioritizing checkout, campaign lifecycle, order operations and payouts.
5. Add stable visual/accessibility coverage and enable the full browser matrix.
6. Require staging release smoke and maintain a PRD-to-test manifest.

## External design basis

This structure follows Playwright's supported setup-project dependencies, isolated browser contexts and reusable authentication state, multiple local web servers, browser/device projects, API request contexts, trace-first CI debugging and axe integration. Authentication files can contain impersonation-capable cookies and therefore belong only in ignored test output.
