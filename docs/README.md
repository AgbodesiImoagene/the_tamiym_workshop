# AI Implementation Guide — Tamiym Workshop

This guide translates the Project Requirements Document (PRD) into technical, implementation-ready instructions for an AI coding agent and human developers. It now also serves as the entry point for repo-state documentation, so it should reflect what is actually implemented in the repository today.

**Source of truth:** the PRD and the client Figma designs. The implementation must maintain functional and visual parity with the approved designs and the PRD scope.  
The PRD defines: public website + customer dashboard + design workshop + checkout/orders + fundraising + admin dashboard + basic analytics, with a hard delivery target. (See PRD.)

## Non-negotiables (must follow)

1. **PRD parity:** implement in-scope features only; do not invent new flows or expand scope.
2. **Design parity:** do not redesign UI. Only small feasibility tweaks allowed (spacing, responsive adjustments) without changing intent.
3. **Nigeria-only initial release:** shipping + payments are Nigeria-only initially.
4. **Paystack-only for now:** implement Paystack as the only payment provider, but via an interface so we can add providers later.
5. **Admin required OOTB:** admin dashboard must support order/product/inventory management + moderation + basic analytics as per PRD.
6. **Built-in observability:** structured logs + metrics + traces (OpenTelemetry preferred).
7. **Monorepo:** single repo with shared packages.
8. **Testing required:** comprehensive unit + integration tests with high coverage; no critical module ships without tests.
9. **Documentation is mandatory and non-negotiable.**
   - API documentation **must** be autogenerated via Swagger/OpenAPI and kept accurate.
   - All public APIs, DTOs, and domain workflows must be documented.
   - Code must include clear inline documentation for:
     - non-trivial business logic
     - state transitions
     - payment, payout, and webhook handling
     - admin-only or security-sensitive logic
   - Documentation must be updated **as part of the same change** whenever behavior or contracts change.
   - Outdated or misleading documentation is considered a defect.
10. **Swagger/OpenAPI is a first-class deliverable, not an afterthought.**
    - Swagger must reflect the real behavior of the system.
    - Endpoints without Swagger annotations are considered incomplete.
    - Changes to request/response shapes must update OpenAPI definitions immediately.

## Mandatory Rule: Prefer Tools and CLIs Over Manual Generation

The AI agent must **always prefer using existing tools, CLIs, and generators**
instead of manually producing output that can be reliably created by tools.

This rule is **strict and non-negotiable**.

### Required behavior

- If a task can be accomplished via a well-known CLI, generator, or automation tool,
  the tool **must be used**.
- Manual generation is only acceptable when:
  1. no suitable tool exists, or
  2. the task is inherently creative or domain-specific.

### Explicit examples (must follow)

- Use official CLIs for project scaffolding:
  - `nest new` for NestJS apps
  - `create-next-app` for Next.js apps
- Use Prisma CLI for all schema and database changes:
  - `prisma init`
  - `prisma migrate`
  - `prisma generate`
- Use Tailwind tooling for design tokens and theme configuration.
- Use OpenTelemetry SDKs and official instrumentation packages instead of custom tracing code.
- Use Paystack SDKs or official API clients where available.
- Use linters, formatters, and code generators rather than hand-formatting.
- Use color pickers, calculators, and validation tools instead of guessing values.
- Use Docker, docker-compose, or platform CLIs rather than ad-hoc scripts.

### Explicitly discouraged behavior

- Hand-writing boilerplate that a CLI would generate.
- Guessing configuration values instead of deriving them via tools.
- Manually crafting migrations instead of using Prisma migrations.
- Writing custom implementations where mature, well-supported libraries exist.

### Enforcement principle

Using tools improves:

- correctness
- consistency
- maintainability
- velocity
- reproducibility

Failure to use appropriate tools is considered a **quality defect**, even if the
resulting code “works”.

## AI Execution Philosophy

The AI agent is expected to behave like a disciplined senior engineer, not a
creative prototype generator.

Priorities, in order:

1. Correctness
2. Maintainability
3. Observability
4. Testability
5. Documentation
6. Speed

Shortcuts that compromise long-term quality are not acceptable, even if they
appear to save time in the short term.

### Documentation + Tooling Rule

Any feature that introduces:

- new API endpoints
- new database schema
- new background jobs
- new external integrations

must include:

- updated Swagger/OpenAPI docs
- updated inline code documentation
- updated tests
- use of official tooling/CLIs where applicable
